Your payload is a public API contract. Consumers parse it, store it, and build workflows on it. These guidelines help you design payloads that age well.

## Use a consistent envelope

Wrap every event in the same top-level shape. Consumers can then route on `type` before parsing `data`.

```json
{
  "type": "invoice.paid",
  "id": "evt_2bX9",
  "created_at": "2026-10-23T09:30:00Z",
  "data": {
    "invoice_id": "inv_8842",
    "customer_id": "cus_1931",
    "amount": 4900,
    "currency": "usd"
  }
}
```

| Field        | Purpose                                                         |
| ------------ | --------------------------------------------------------------- |
| `type`       | Same as the event type, so the body is self-describing.         |
| `id`         | Your event ID. Also pass it as `event_id` for deduplication.    |
| `created_at` | When the event happened, not when it was delivered.             |
| `data`       | The event-specific content.                                     |

## Thin or fat payloads

<Tabs>
  <Tab title="Fat payloads">
    Include the full object state in `data`.

    - **Pros:** Consumers don't need an extra API call.
    - **Cons:** Larger messages, and stale data if events arrive out of order.

    Best for small objects and consumers without API access.
  </Tab>
  <Tab title="Thin payloads">
    Include only IDs and what changed, and let consumers fetch the rest from your API.

    - **Pros:** Small, always-fresh data, and no sensitive fields in transit.
    - **Cons:** Consumers need API credentials and make extra calls.

    Best for large or sensitive objects.
  </Tab>
</Tabs>

## Rules of thumb

<AccordionGroup>
  <Accordion title="Use stable, explicit types">
    Send amounts as integers in the smallest currency unit (`4900`, not `49.00`). Send timestamps as ISO 8601 strings in UTC.
  </Accordion>
  <Accordion title="Never include secrets">
    Leave out passwords, full card numbers, API tokens, and other credentials. Payloads are stored in logs for the retention period.
  </Accordion>
  <Accordion title="Only add, never change">
    Adding optional fields is safe. Renaming, removing, or changing a field's type is a breaking change that needs a new event type version.
  </Accordion>
  <Accordion title="Keep payloads small">
    The maximum is 1 MB, but aim for under 20 KB. Large payloads are slower to deliver and to verify.
  </Accordion>
  <Accordion title="Help with ordering">
    Delivery order isn't guaranteed. Include `created_at` or a version number so consumers can discard stale updates. See [Ordering](/delivery/ordering).
  </Accordion>
  <Accordion title="Use snake_case consistently">
    Pick one naming style for keys and use it everywhere. Hookline examples use `snake_case`.
  </Accordion>
</AccordionGroup>

## Document every payload

Attach a JSON Schema to each [event type](/sending/event-types) and publish it in the [event catalog](/sending/event-catalog). Consumers then always see the current shape.
